# Replication Recipe — Build a New Game Design Tool

Operational walkthrough referenced by `SKILL.md`. Uses Arrow3D as the worked example throughout.

## Step 0 — Decide what kind of game

| Genre | Primitive | Pipeline applies? |
|---|---|---|
| Tile/grid puzzle (match-3, sokoban, polycube) | grid or voxel | Yes — full Tier 2 |
| Card/deck game | card-instance | Partial — Stage 1-2 only (no geometry) |
| Tower defense | path/waypoint | Yes — geometry + wave-sequence variant |
| RPG/encounter | encounter graph + items | Partial — Tier 1 + content injection only |
| Platformer | tilemap | Yes — full Tier 2 |
| Hand-authored narrative | none | Tier 1 only — no procgen value |

**Rule of thumb:** Tier 2 (pipeline) earns its keep at 50+ pieces of generated content with progression scaling. Below that, manual authoring + Tier 1 is fine.

## Step 1 — Start from GameDesignToolTemplate

```bash
gh repo create your-org/your-game-tool --template The1Studio/GameDesignToolTemplate --public
git clone git@github.com:your-org/your-game-tool.git
cd your-game-tool
npm install
npm run dev
```

Out of the box (v2.0+):
- React 19 + TS + Vite shell
- IndexedDB persistence
- Schema-driven tables + forms
- Built-in modules: items, economy, progression, **curriculum, level pool, comparison, schema migrations, stats dashboard**

Pre-v2 (v1.x): only items, economy, progression. Upgrade to v2 to get the full pipeline scaffold.

## Step 2 — Define your geometry primitive

Examples by game type:

| Game | Primitive | Field shape |
|------|-----------|-------------|
| Tile puzzle | `{x, y}` | `Vector2Int` |
| Polycube (Arrow3D) | `{Face, VoxelPosition}` (`SurfacePosition`) | one-cell-per-face on 3D voxel surface |
| Hex grid | `{q, r}` (axial coords) | hex coordinate |
| Card | `{cardId, deckPosition}` | flat list |
| Path (TD) | `[Vector2Int, ...]` (waypoints) | sequence |

Rules:
- **SSOT** — store the primitive, not derivations. (Arrow3D rule: store `Cells`, compute `Size` from bounding box; never store `Size`.)
- **Zod-typed** — table+form scaffolding is free
- **`validate()` function** — catches geometry violations (e.g., overlapping cells, disconnected components, occluded faces)

## Step 3 — Define content primitives

For each kind of in-level content, decide three properties:

| Question | Examples (Arrow3D) |
|---|---|
| Auto-place vs designer-place? | Arrows = auto; PausePoint/Transitor = designer |
| Independent or relational? | Arrows reference cells (relational) |
| Sequenced or set? | Arrows form a chain (sequenced); elements are set |

Arrow3D split:
- **Auto:** Arrows (path-based, generated by walker)
- **Designer-hinted:** PausePoint, ChangeDirection, DualArrow, Transitor (per-L target counts shown in editor banner; designer places by hand)

The split matters because it determines pipeline staging — Stage 3a runs auto, Stage 3b is designer authorship.

## Step 4 — Build the pipeline

### 4.1 Shape-only generator (Stage 1)

Pure geometry. Empty content. Output to `data/<batch-name>/`.

**Arrow3D parallel:** `scripts/gen-symbol-shapes.mjs`. Adapt to your geometry primitive.

Instant-by-design. If your shape gen takes seconds per shape, you've baked content in — pull it out.

### 4.2 Curriculum picker (Stage 2)

Read progression curve → for each L-slot, score candidate shapes by abstract metrics (size bucket, category, variety rules). Output 1 shape per slot.

**Arrow3D parallel:** `scripts/build-level-curriculum.mjs`. Picker is content-blind; copy the structure, change the scoring rules.

Scoring rules for Arrow3D (adapt for your game):
- Size bucket from progression curve
- Family rotation (cube → box → letterDigit → polycube)
- Special-rect ratio (1-2 RECT → 1 SPECIAL)
- Avoid duplicate shapes within last N slots

### 4.3 Content injectors (Stage 3a + 3b)

**Auto injector (3a):** batch script + Web Worker pair, both calling shared engine library. Don't duplicate logic.

**Arrow3D parallel:** `scripts/level-generate-arrow.mjs` + `workers/generator.worker.ts` → both call `generator/index.ts`.

**Designer-hinted injector (3b):** module UI shows per-L target counts as banner; designer authors content; tool validates totals against curve.

**Arrow3D parallel:** `scripts/inject-elements.mjs` for batch; in-editor placement for one-off.

### 4.4 Validators (Stage 4)

Two minimum:
1. **Geometry validator** — primitive constraints (no overlaps, no disconnects, no occlusions)
2. **Solvability validator** — content can resolve its goal (every primitive can reach its target state)

These run in tool **and** engine. Bake the same Zod schema + validator functions into both codebases.

**Arrow3D parallel:** `LevelShapeValidator` + `ArrowReachabilityValidator`, mirrored in Unity `LevelParamsLoader`.

### 4.5 Engine writer (Stage 5)

JSON output to engine's asset folder. Schema agreed in writing. Optional encrypted mirror.

**Arrow3D parallel:** write to `../UnityArrow3D/Assets/Level Json/`, EncryptedData mirror managed by separate Unity-side step.

## Step 5 — Wire the engine consumer

In the engine codebase:
1. Define the same level JSON schema (Zod or engine-native)
2. Run the same validators on load — fail loudly, no silent fallback
3. Load levels from the tool's output folder
4. Tool **never** edits engine source; bug findings → audit reports under `plans/<date>-<slug>/`

**Arrow3D parallel:** Unity reads `Assets/Level Json/`, runs `LevelShapeValidator` + `ArrowReachabilityValidator`, throws `LevelValidationException` on failure.

## What Arrow3D-specific NOT to copy

If your game isn't Arrow3D:
- Polycube/voxel surface geometry (`SurfacePosition`, `CuboidConfig`, `FaceGeometry`)
- Arrow walker (game-specific path resolver in `lib/walker.ts`)
- Element types (PausePoint/ChangeDirection/DualArrow/Transitor — Arrow3D mechanics)
- `gen-symbol-shapes.mjs` symbol catalog (alphabet/digits/symbols specific to Arrow3D's letter-shape levels)
- `prod-batch-v*` data pools

**Copy the patterns, not the content.**

## Common adaptation traps

| Trap | Symptom | Fix |
|---|---|---|
| Reusing Arrow3D's voxel primitive for 2D game | Awkward face/normal logic where you only need x/y | Define your own primitive; throw out the 3D code path |
| Single-script shape gen + content injection | "Why does shape gen take 3 minutes per shape?" | Split into Stage 1 + Stage 3a; never bake content during gen |
| Picker references content fields | Refactor of content algorithm cascades into picker rewrite | Picker reads geometry only; content injection lives in its own stage |
| Tool validators drift from engine validators | Levels that pass tool validation crash on load in engine | Lift validators into shared lib; both codebases import same source |
| Trying to do A/B variants before solver | Variants tagged but no way to know which is "harder" | Ship 3.1 solver first; A/B is downstream |

## Hardening graduation triggers

Move Tier 2 → Tier 3 when ANY of these happen:
- Curriculum picker output starts feeling "off" (gut says easier/harder than intended)
- Designers complain about not knowing which L-slots are over/under-covered
- A schema change broke historical level data
- Engine playtests reveal levels that "should" be L50 but everyone fails at L20

Order to ship (low cost → high cost):
1. **Schema migrations (3.3)** — cheap; naturally portable; ship first
2. **Stats dashboard (3.4)** — read-only surfaces gaps; designers self-serve
3. **Solver (3.1)** — validates curriculum intent; closes loop on (1)
4. **Telemetry (3.2)** — needs engine-side log emission; closes loop on (3)
5. **A/B variants (3.5)** — once telemetry exists, multiplies throughput
